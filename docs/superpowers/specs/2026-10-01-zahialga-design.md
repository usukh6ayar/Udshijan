# Захиалга — 3-р үе шат: checkout DB рүү, демо төлбөр, admin удирдлага

Огноо: 2026-10-01
Төлөв: батлагдсан, хэрэгжүүлэхэд бэлэн
Өмнөх үе шат: `2026-09-13-admin-huudas-design.md` (DB + admin бүтээгдэхүүн CRUD)

## Зорилго

Өнөөдөр checkout захиалгыг хаана ч хадгалдаггүй: санамсаргүй дугаар үүсгээд
сагсыг хоосолдог. Захиалга шалгах форм (`OrderLookup`) үргэлж «олдсонгүй»
гэдэг. Энэ үе шатаар:

- захиалга Postgres-д хадгалагдана, барааны үлдэгдэл хасагдана;
- хэрэглэгч демо төлбөрийн урсгалаар явж, захиалгаа дараа нь шалгаж чадна;
- admin захиалгыг харж, төлбөрийг баталгаажуулж, дуусгаж, цуцалж чадна.

## Хамрах хүрээ

Багтах зүйл:

- `orders` хүснэгт, `placeOrder` Server Action (нэг transaction)
- `lib/pricing.ts` — сагс, checkout, сервер гурвын ганц үнийн тооцоо
- Купоны хөнгөлөлт нийт дүнгээс хасагддаг болох (одоогийн алдаа)
- Шинэ зочин хоосон сагсаар эхлэх (демо `SEED` сагсыг хасна)
- `/zahialga/[number]` — захиалгын хуудас, демо төлбөр
- `OrderLookup` — дугаар + утсаар хайх
- `/admin/zahialga`, `/admin/zahialga/[number]`
- Локал хөгжүүлэлт Neon dev branch дээр

Багтахгүй зүйл:

- Жинхэнэ QPay / карт — дараагийн үе шат. Энэ үе шатад демо симуляц.
- Хэрэглэгчийн аккаунт, «миний захиалгууд»
- SMS / и-мэйл мэдэгдэл
- Өнгө, хэмжээ тус бүрийн үлдэгдэл — зөвхөн барааны нийт `stock`
- Төлөгдөөгүй захиалгыг автоматаар цуцлах, spam хамгаалалт
- Хэрэглэгч өөрөө захиалга цуцлах
- Борлуулалтын самбар (4-р үе шат)

## Өгөгдөл

### `orders` хүснэгт

| Багана | Төрөл | Тайлбар |
|---|---|---|
| `number` | text PK | `UDS-YYMMDD-NNNN`, серверт үүсгэнэ |
| `status` | text | `new` / `done` / `cancelled` |
| `paidAt` | timestamptz null | төлөгдсөн мөч |
| `paidVia` | text null | `demo` (хэрэглэгч демо дээр дарсан) / `admin` (гараар) |
| `accessKey` | text | санамсаргүй 32 байт, захиалагчийн cookie-д |
| `name`, `phone`, `email` | text | `email` хоосон байж болно |
| `city`, `district`, `khoroo`, `address` | text | `pickup` үед `khoroo`, `address` хоосон |
| `note` | text | хоосон байж болно |
| `shipping` | text | `standard` / `express` / `pickup` |
| `payment` | text | `qpay` / `card` / `transfer` / `cash` |
| `items` | jsonb | `OrderItem[]`, доор |
| `subtotal`, `couponDiscount`, `shippingFee`, `total` | integer | төгрөг |
| `couponCode` | text null | |
| `createdAt` | timestamptz | `now()` |

```ts
type OrderItem = {
  slug: string;
  title: string;   // захиалгын үеийн хуулбар
  sku: string;
  color?: string;
  size?: string;
  qty: number;
  unitPrice: number; // захиалгын үеийн үнэ
};
```

`items` нь хуулбар: дараа нь барааны нэр, үнэ өөрчлөгдөх эсвэл бараа устсан ч
захиалга зөв хэвээр харагдана. Борлуулалтын тооцоо хэрэгтэй бол
`jsonb_array_elements`-ээр задална. Тусдаа `order_items` хүснэгт нь одоогийн
хэмжээнд илүүдэл.

**Захиалгын дугаар:** `UDS-` + `YYMMDD` (Улаанбаатарын цагаар) + 4 оронтой
санамсаргүй тоо. Primary key давхардвал шинэ дугаараар дахин оролдоно, 5
удаагийн дараа алдаа. Хэлбэр нь `OrderLookup`-ийн одоогийн
`/^UDS-\d{6}-\d{4}$/` шалгалттай нийцнэ.

`paidAt` нь `status`-аас тусдаа. Гурван төлөв (`new` → `done`, эсвэл
`cancelled`) нь захиалгын явц, `paidAt` нь төлбөрийн баримт.

## Үнийн тооцоо — `lib/pricing.ts`

Цэвэр функц. Клиентийн сагс (`lib/cart.ts`), checkout (`CheckoutView`),
серверийн `placeOrder` гурвуулаа үүнийг дуудна.

```ts
computeTotals({
  lines: { unitPrice: number; compareAt?: number; qty: number }[],
  couponCode: string | null,
  shipping: "standard" | "express" | "pickup",
}): {
  subtotal: number;
  savings: number;        // compareAt-аас хэмнэсэн, зөвхөн харуулах
  couponCode: string | null; // хүчингүй код → null
  couponDiscount: number;
  shippingFee: number;
  total: number;          // subtotal − couponDiscount + shippingFee
  vat: number;            // total дотор багтсан НӨАТ, зөвхөн харуулах
}
```

Дүрмүүд:

- `couponDiscount = round(subtotal × хувь)`. Купоны жагсаалт (`NAIM8` = 15%)
  `lib/cart.ts`-ээс энд шилжинэ.
- **`total`-оос купоны хөнгөлөлтийг хасна.** Өнөөдөр `computeTotals` нь
  `couponSavings`-ийг тооцоолсон ч `total = subtotal + shipping` гэж бодож,
  `OrderSummary` хөнгөлөлтийг огт харуулдаггүй. Сагсанд «✓ NAIM8 · −15%»
  гэж бичигдсэн ч дүн буурдаггүй.
- Хүргэлт: `pickup` → 0, `express` → 10 000, `standard` → `subtotal ≥ 100 000`
  бол 0, бусад үед 5 000. Босгыг купоноос өмнөх `subtotal`-аар тооцно
  (өнөөдрийн дүрэм хэвээр).
- `OrderSummary` купоны мөрийг нэмж харуулна.

`EXPRESS_FEE`, `FREE_SHIPPING_FROM`, `SHIPPING_FEE`, `VAT_RATE` бүгд энэ модульд
шилжинэ.

## Хэрэглэгчийн урсгал

### Сагс

`lib/cart.ts`-ийн `SEED` (3 бараа + `NAIM8`) хасагдаж, шинэ зочин хоосон
сагсаар эхэлнэ.

### Захиалах — `placeOrder`

`lib/orders/actions.ts` дахь Server Action. Оролт: сагсны мөрүүд
`{slug, color, size, qty}[]`, купоны код, формын талбарууд. **Үнэ, дүнг
клиентээс авахгүй.**

1. Формыг серверт шалгана. Одоогийн клиент талын `validate()`-ийг
   `lib/orders/validate.ts` руу гаргаж хоёр тал хуваалцана.
2. Мөр бүрийн `qty` нь 1–20 бүхэл тоо. Хоосон сагс татгалзана.
3. Нэг transaction дотор:
   - мөр бүрт `UPDATE products SET stock = stock - $qty WHERE slug = $slug
     AND stock >= $qty RETURNING ...` — нэг ч мөр буцаагүй бол бүгдийг
     rollback хийж, ямар бараа хэдэн ширхэг үлдсэнийг буцаана;
   - нэг барааг өөр өнгө/хэмжээгээр хоёр мөрөнд авсан бол `qty`-г slug-аар
     нэгтгэж нэг удаа хасна;
   - DB-ийн үнээр `computeTotals` дуудна;
   - `orders`-д бичнэ.
4. Transaction-ы дараа `updateTag("products")` болон бараа бүрийн
   `updateTag("product-" + slug)` — үлдэгдэл дэлгүүрт шууд тусна.
5. Захиалагчийн браузерт `udshijan_order_<number>` httpOnly cookie
   (`accessKey`, 30 хоног, `SameSite=Lax`, production дээр `Secure`).
6. Буцаах утга: `{ number }` — клиент сагсаа хоосолж `/zahialga/<number>`
   руу шилжинэ. Алдаатай бол `{ errors }` — сагс хэвээр үлдэнэ.

### Захиалгын хуудас — `/zahialga/[number]`

Хандах эрх: тухайн захиалгын cookie таарвал, эсвэл утасны дугаар оруулж
таарвал. Аль нь ч үгүй бол утас асуух форм харуулна. Буруу утсанд болон
байхгүй дугаарт ижил «олдсонгүй» хариу өгнө — дугаар байгаа эсэхийг
таамаглуулахгүй.

Харуулах зүйл: төлөв, төлбөрийн байдал, бараа, хаяг, дүн. Төлбөрийн хэлбэрээс:

- **QPay / Карт**, төлөгдөөгүй бол: «Симуляц — бодит мөнгө шилжихгүй» гэсэн
  тодорхой тэмдэглэгээтэй DEMO QR (эсвэл картын хэсэг) ба «Төлбөр төлөгдсөн
  гэж тэмдэглэх» товч → `markDemoPaid` Server Action (`paidVia = "demo"`).
  `urgoo-soh`-ийн `qpay-dialog`-ийн хэв маяг.
- **Шилжүүлэг**: дансны мэдээлэл, гүйлгээний утгад захиалгын дугаараа бичих
  заавар. Дансны мэдээлэл `lib/data/store.ts`-д, жинхэнэ данс өгөгдөх хүртэл
  «Демо данс» гэж тэмдэглэсэн утгатай.
- **Бэлэн**: «Хүргэлтийн үед төлнө».

`markDemoPaid` нь хуудастай ижил эрх шалгана (cookie эсвэл утас) ба зөвхөн
`payment ∈ {qpay, card}`, `status = new`, `paidAt = null` үед ажиллана.

### Захиалга шалгах — `OrderLookup`

Дугаар + утас. Server Action хоёуланг нь шалгаж, таарвал тухайн захиалгын
cookie-г тавиад `/zahialga/<number>` руу шилжүүлнэ. Таараагүй бол
«олдсонгүй». Демо мессеж («Энэ бол демо дэлгүүр тул…») хасагдана.

Утсыг харьцуулахдаа зөвхөн цифрийг нь харьцуулна (`9911-2233` = `99112233`).

## Admin

Admin хуудасны толгойд «Бүтээгдэхүүн | Захиалга» таб.

### `/admin/zahialga`

Шинэ нь эхэндээ, `?status=new|done|cancelled|all` шүүлт (анхдагч `new`).
Мөр бүрт: дугаар, нэр, утас, дүн, төлбөр (Төлөгдөөгүй / Төлөгдсөн /
Төлөгдсөн (демо)), огноо.

### `/admin/zahialga/[number]`

Бүх мэдээлэл ба төлөвөөс хамаарах товч:

| Товч | Хэзээ гарах | Үйлдэл |
|---|---|---|
| Төлбөр төлөгдсөн гэж тэмдэглэх | `paidAt = null`, `status ≠ cancelled` | `paidAt = now`, `paidVia = admin` |
| Дууссан болгох | `status = new` | `status = done` |
| Цуцлах | `status = new` | нэг transaction: `status = cancelled` + `items`-ийн тоог үлдэгдэлд буцааж нэмнэ |

Цуцлахад бараа DB-ээс устсан бол түүний үлдэгдлийг алгасна. Дууссан
захиалгыг цуцлахгүй. Цуцалсны дараа `updateTag("products")` ба барааны
тагууд.

Төлөв шилжих бүх action `WHERE status = 'new'` гэх мэт нөхцөлтэй update
хийж, мөр өөрчлөгдөөгүй бол «Захиалгын төлөв өөрчлөгдсөн байна» гэж буцаана
— хоёр таб зэрэг дарахад давхар буцаалт гарахгүй.

### Эрх

Action бүрийн эхэнд `requireAdmin()`, хуудасны Suspense доторх компонентод
`requireAdminPage()` — 1-р үе шатын хэв маяг.

## Кэш

Захиалгыг кэшлэхгүй — `use cache` хэрэглэхгүй. Захиалгын хуудас cookie
уншдаг, admin хуудсууд session уншдаг тул хүсэлт бүрт шинээр уншина.
Захиалгын өгөгдлийг уншдаг компонент бүр Suspense дотор, `cookies()`-ийн
дараа уншина.

## Алдаа боловсруулалт

| Нөхцөл | Хариу |
|---|---|
| Үлдэгдэл хүрэлцэхгүй | Захиалга үүсэхгүй. «“<нэр>” — ердөө N ширхэг үлдсэн» (0 бол «дууссан») |
| Сагсны бараа DB-д алга | «Сагсанд байгаа зарим бараа зарагдахаа больсон», тэр мөрийг нэрлэнэ |
| Формын алдаа | Талбар бүрийн доор, одоогийн `Field` `error` prop |
| DB хүрэхгүй | «Захиалга түр хүлээж авах боломжгүй, дахин оролдоно уу», сагс хэвээр |
| Дугаар давхардал 5 удаа | DB хүрэхгүйтэй ижил мессеж |

## Хүлээн зөвшөөрсөн эрсдэл

Хэн ч төлбөргүйгээр захиалга өгч үлдэгдлийг түгжиж болно. Admin цуцлахад
буцна. Мөр бүрийн 20 ширхэгийн хязгаар зөвхөн нэг удаагийн хор хөнөөлийг
хязгаарлана. Автомат цуцлалт, rate limit нь жинхэнэ төлбөрийн үе шатад.

## Тест

Vitest, DB-г mock хийнэ (`lib/admin/actions.test.ts`-ийн хэв маяг):

- `computeTotals`: купон хасагдах, хүчингүй купон, хүргэлтийн босго,
  `express`, `pickup`
- `placeOrder`: формын шалгалт, `qty` хязгаар, хоосон сагс, клиентээс ирсэн
  үнэ огт ашиглагдахгүй, үлдэгдэл хүрэлцэхгүй үед юу ч бичигдэхгүй, нэг
  барааны хоёр мөрийг нэгтгэх
- Хандах эрх: cookie буруу / утас буруу / байхгүй дугаар → ижил хариу
- `markDemoPaid`: зөвхөн qpay/card, зөвхөн төлөгдөөгүй `new`
- Admin action: нэвтрээгүй үед татгалзах, цуцлахад үлдэгдэл буцах,
  давхар цуцлалт хоёр дахь удаа юу ч хийхгүй

E2E (локал `next start` + headless Chromium, Neon dev branch дээр): захиалах →
демо төлбөр → `/zahialga` дээр харагдах → өөр браузерт утсаар шалгах →
admin дээр харагдах → цуцлах → дэлгүүрт үлдэгдэл буцсан.

## Хөгжүүлэлтийн орчин

Локал `.env.local` одоо production-ий Neon DB рүү заадаг. Энэ үе шатаас
эхлэн локал хөгжүүлэлт **Neon dev branch** дээр явна:

1. Хэрэглэгч Neon console дээр production-аас `dev` branch үүсгэнэ.
2. `.env.local`-ийн `DATABASE_URL`-ийг тэр branch-ийн холболтоор солино.
3. `npx drizzle-kit push` нь dev branch дээр `orders` хүснэгтийг үүсгэнэ.

Production-д `orders` хүснэгтийг deploy-ийн өмнө `drizzle-kit push`-ээр
production холболт дээр үүсгэнэ.

## Deployment

Шинэ env хувьсагч байхгүй. 1-р үе шатын `ADMIN_PASSWORD`,
`ADMIN_SESSION_SECRET` Vercel production-д тохируулагдсан байх ёстой.
